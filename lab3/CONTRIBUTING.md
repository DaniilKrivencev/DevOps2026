# Правила внесения изменений — ЛР3

Любое изменение в `lab3/` проходит через единый локальный проверочный контур:

```bash
make verify
```

Коммит, слияние ветки и сдача работы **запрещены**, если `make verify` завершается с ошибкой.

## Что запускает `make verify`

| Шаг | Команда | Что проверяет |
|-----|---------|---------------|
| 1 | `make policy` | правила ниже (пропуски тестов, пороги, исключения анализаторов) |
| 2 | `make lint` | `ruff check` + `ruff format --check` (стиль, импорты, bugbear, security-правила) |
| 3 | `make sast` | `bandit` — статический анализ безопасности, отчёт `reports/bandit.json` |
| 4 | `make migrate-check` | цепочка миграций на чистой БД + `alembic check` (модели = миграции) |
| 5 | `make test` | unit + интеграционные тесты, JUnit и покрытие в `reports/`, порог покрытия |
| 6 | `make mutation` | мутационное тестирование бизнес-правил, порог mutation score |

## Запрещено без обоснования (п. 14)

Нарушения обнаруживает `scripts/check_policy.py` (шаг `make policy`):

1. **Пропуск тестов** — `pytest.mark.skip`, `skipif`, `xfail`, `pytest.skip()`.
   Допустимо только если в `reason` есть слово «обоснование»
   (пример: PostgreSQL-тест пропускается, когда не задан `TEST_DATABASE_URL`, и запускается через `make test-pg`).
2. **Снижение порогов** — `fail_under` в `pyproject.toml` не ниже 85,
   `MUTATION_MIN` в `Makefile` не ниже 90. Удаление `--strict-markers` запрещено.
3. **Исключения анализаторов**:
   - `# noqa` / `# nosec` — только с кодом правила (`# noqa: F401`, `# nosec B603`)
     **и** пояснением: в той же строке после «—» или комментарием «Обоснование: …» строкой выше;
   - новые `ignore` / `per-file-ignores` в ruff и `skips` в bandit — только через
     изменение списка разрешённых исключений в `scripts/check_policy.py` в той же ветке,
     с обоснованием комментарием в `pyproject.toml`.
4. **Удаление шага из `make verify`** — политика проверяет, что `verify` вызывает все обязательные шаги.

Базовые пороги и разрешённые исключения хранятся в `scripts/check_policy.py`.
Этот файл, `pyproject.toml`, `Makefile` и `alembic/versions/*` — **критические файлы приёмки**:
их изменение отдельно проверяется вторым участником команды при слиянии.

## Миграции

- Любое изменение моделей сопровождается новой миграцией (`make migrate-new MSG="..."`).
- Применённые миграции не редактируются — только новая ревизия.
- Миграция должна работать на БД с данными (значения по умолчанию через `server_default`,
  для SQLite — `batch_alter_table`) и иметь рабочий `downgrade`.
- `make migrate-check` упадёт, если модели и миграции разошлись.

## Ветки и слияние

- Работа ведётся в ветках `lab3/<тема>`, слияние — `git merge --no-ff` после `make verify`.
- Конфликт слияния разрешается вручную с сохранением изменений обеих веток,
  затем обязательно `make verify` и коммит слияния с описанием конфликта
  (см. `docs/MERGE_CONFLICT.md`).
