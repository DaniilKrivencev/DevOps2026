# Техническое задание
## Система учёта Городской Думы
### ГОСТ 19.201-78 / ГОСТ 34.602-89

---

## 1. Введение

### 1.1 Наименование системы
**Городская Дума** — информационная система учёта депутатов, комиссий, заседаний и посещаемости.

### 1.2 Назначение системы
Система предназначена для автоматизации учёта деятельности представительного органа местного самоуправления: регистрации депутатского корпуса, постоянных комиссий, проводимых заседаний и фиксации явки депутатов.

### 1.3 Область применения
Секретариат и администрация городской думы.

---

## 2. Требования к системе

### 2.1 Функциональные требования

#### 2.1.1 Управление депутатами
- Ф1.1 Система должна обеспечивать создание, просмотр, изменение и удаление записей о депутатах.
- Ф1.2 Запись о депутате включает: ФИО, политическую партию, избирательный округ, дату избрания, статус активности.
- Ф1.3 Система должна отображать список всех депутатов с возможностью фильтрации.

#### 2.1.2 Управление комиссиями
- Ф2.1 Система должна обеспечивать создание, просмотр, изменение и удаление постоянных комиссий.
- Ф2.2 Каждая комиссия имеет: название (уникальное), описание, председателя.
- Ф2.3 Система должна управлять составом комиссии (добавление/удаление членов).
- Ф2.4 **[Бизнес-правило]** Председатель комиссии обязан входить в состав комиссии. Нарушение правила запрещено на уровне API.

#### 2.1.3 Управление заседаниями
- Ф3.1 Система должна обеспечивать регистрацию заседаний комиссий с указанием даты, темы и статуса.
- Ф3.2 Статусы заседания: «Запланировано», «Проведено», «Отменено».
- Ф3.3 **[Бизнес-правило]** Перевод заседания в статус «Проведено» разрешён только при наличии кворума — более 50% членов комиссии отмечены как «Присутствовал».

#### 2.1.4 Учёт посещаемости
- Ф4.1 Система должна фиксировать явку каждого депутата на каждое заседание.
- Ф4.2 Статусы посещаемости: «Присутствовал», «Отсутствовал», «Уважительная причина».
- Ф4.3 Для одной пары «депутат + заседание» допускается только одна запись посещаемости.
- Ф4.4 Система должна поддерживать фильтрацию посещаемости по заседанию и по депутату.

#### 2.1.5 Служебные функции
- Ф5.1 Система предоставляет HTTP-endpoint `/health` для проверки работоспособности и соединения с БД.
- Ф5.2 Веб-интерфейс предоставляет доступ ко всем сущностям через браузер.
- Ф5.3 REST API предоставляет интерактивную документацию (OpenAPI/Swagger).

### 2.2 Нефункциональные требования

| № | Требование | Значение |
|---|-----------|---------|
| НФ1 | Доступность | 99.9% в рабочее время |
| НФ2 | Время ответа API | < 500 мс для любого запроса |
| НФ3 | Безопасность | Все секреты через переменные окружения, не в коде |
| НФ4 | Переносимость | Docker-контейнер, запускается на любой ОС |
| НФ5 | Масштабируемость | Архитектура позволяет горизонтальное масштабирование |

## 3. Сущности и связи

### 3.1 Перечень сущностей

| Сущность | Таблица | Описание |
|----------|---------|----------|
| Депутат | `deputies` | Член городской думы |
| Комиссия | `commissions` | Постоянная рабочая комиссия |
| Членство | `commission_members` | M2M: принадлежность депутата к комиссии |
| Заседание | `sessions` | Формальное заседание комиссии |
| Посещаемость | `attendances` | Явка депутата на конкретное заседание |

### 3.2 Связи

```
Deputy    (1) ──── (*) CommissionMember (*) ──── (1) Commission
Deputy    (1) ──── (*) Attendance
Session   (1) ──── (*) Attendance
Commission(1) ──── (*) Session
Deputy    (1) ──── (*) Commission [через chair_id]
```

---

## 4. Ограничения и правила хранения данных

### 4.1 Ограничения целостности
- `commissions.name` — уникально
- `commission_members(commission_id, deputy_id)` — уникально
- `attendances(session_id, deputy_id)` — уникально
- Каскадное удаление: при удалении комиссии удаляются её членства и заседания
- При удалении депутата, который является председателем, `chair_id` становится NULL

### 4.2 Требования к хранению
- СУБД: PostgreSQL 16+
- Схема создаётся и управляется через Alembic-миграции
- Резервное копирование: `make backup` (pg_dump), хранение в директории `backups/`
- Восстановление: `make restore BACKUP=<файл>`

## 5. Обработка ошибок

| Сценарий | HTTP-код | Сообщение |
|----------|----------|-----------|
| Ресурс не найден | 404 | `"Deputy not found"` |
| Дублирующая запись | 409 | `"Deputy is already a member"` |
| Нарушение бизнес-правила (председатель не член) | 422 | `"Business rule violation: chair must be a member..."` |
| Нарушение бизнес-правила (нет кворума) | 422 | `"Quorum not met: X/Y present..."` |
| Невалидные данные | 422 | Подробное описание от Pydantic |
| Ошибка сервера | 500 | Стандартный ответ FastAPI |

## 6. Конфигурация

Все параметры конфигурации передаются через переменные окружения.  
Шаблон: `.env.example`. Реальные значения: `.env` (не коммитится).

| Переменная | Обязательна | Описание |
|---|---|---|
| `DATABASE_URL` | Да | DSN для SQLAlchemy (asyncpg) |
| `POSTGRES_USER` | Да | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Да | Пароль PostgreSQL |
| `POSTGRES_DB` | Да | Имя базы данных |
| `SECRET_KEY` | Да | Ключ для подписи токенов |
| `APP_ENV` | Нет | `development` / `production` |
| `DEBUG` | Нет | `true` / `false` |

## 7. Интерфейс

### 7.1 HTTP API
- REST API на базе FastAPI
- Формат данных: JSON
- Версионирование: `/api/v1/`
- Документация: Swagger UI на `/docs`, ReDoc на `/redoc`

### 7.2 Веб-интерфейс
- Шаблонизатор Jinja2
- Bootstrap 5 (адаптивный дизайн)
- Маршруты: `/`, `/ui/deputies`, `/ui/commissions`, `/ui/sessions`, `/ui/attendance`
- CRUD-операции через модальные формы без перезагрузки страницы
