# Правила внесения изменений — CONTRIBUTING

Документ фиксирует **обязательный процесс** для любого изменения в проекте.

---

## 1. Жизненный цикл изменения

```
задача (Issue)
  → отдельная ветка
    → локальные проверки (make verify)
      → коммиты (осмысленные, атомарные)
        → Pull Request / Merge Request
          → code review
            → merge в main
              → тег версии (при релизе)
```

---

## 2. Обязательные команды перед коммитом

```bash
make verify   # = make quality + make test
```

**Запрещено** делать коммит, если `make verify` завершается с ошибкой.

---

## 3. Правила работы с ветками

| Тип ветки | Шаблон имени | Пример |
|-----------|-------------|--------|
| Новая функция | `feature/<описание>` | `feature/add-quorum-check` |
| Исправление ошибки | `fix/<описание>` | `fix/attendance-duplicate` |
| Документация | `docs/<описание>` | `docs/update-api` |
| Рефакторинг | `refactor/<описание>` | `refactor/extract-service` |

- Ветка создаётся **от актуального `main`**.
- Ветка **не содержит** несвязанных изменений.
- Удаляется после слияния.

---

## 4. Правила коммитов

Используется [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

**Типы**: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`

Примеры:
```
feat(deputies): add is_active filter to list endpoint
fix(sessions): fix quorum calculation when no members
docs(api): document attendance endpoints
test(commissions): add membership business rule tests
```

---

## 5. Pull Request

Каждый PR должен:
- [ ] Содержать ссылку на задачу (Issue)
- [ ] Пройти `make verify` без ошибок
- [ ] Иметь понятное описание изменения
- [ ] Включать тесты для новой функциональности
- [ ] Быть проверен хотя бы одним другим участником команды

---

## 6. Критические файлы приёмки

Изменения в следующих файлах требуют **отдельной проверки** в PR:

| Файл | Причина |
|------|---------|
| `Makefile` | Изменение обязательных команд проверки |
| `docker-compose.yml` | Изменение инфраструктуры |
| `alembic/versions/*.py` | Изменение схемы БД |
| `pyproject.toml` | Изменение настроек качества кода |
| `.gitignore` | Риск утечки секретов |
| `CONTRIBUTING.md` | Этот документ |

---

## 7. Запрещённые действия

- ❌ Удалять или отключать тесты
- ❌ Снижать пороги качества (ruff)
- ❌ Коммитить файл `.env` или любые секреты
- ❌ Делать `git push --force` в `main`
- ❌ Сливать ветку без прохождения `make verify`
- ❌ Обходить проверки через `# noqa` без обоснования в комментарии

---

## 8. Версионирование

Используется [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`

```bash
# Создать тег релиза
git tag -a v0.1.0 -m "Initial release"
git push origin v0.1.0
```

| Тип изменения | Версия |
|---|---|
| Несовместимые изменения API | MAJOR |
| Новая функциональность (обратно совместима) | MINOR |
| Исправления ошибок | PATCH |

---

## 9. Конфигурация через переменные окружения

- Все конфигурационные значения **только через переменные окружения**
- Шаблон значений — в `.env.example`
- Реальные значения — в `.env` (никогда не коммитится!)
- Для CI используются переменные в секретах репозитория

---

## 10. Порядок приёмки на защите

1. Показать путь изменения от задачи до тега версии
2. Объяснить все файлы, команды и решения
3. Внести небольшое изменение через ветку и PR
4. Показать `make verify` — все проверки должны проходить
5. Показать, что `.env` и локальные файлы не в репозитории
6. Продемонстрировать `make up` и работу приложения
7. Показать работающий `/health` endpoint
