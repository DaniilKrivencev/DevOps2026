# Правила внесения изменений — CONTRIBUTING

Документ фиксирует **обязательный процесс** для любого изменения в проекте
«Городская Дума». Действует для всех лабораторных работ: все результаты
хранятся в одном репозитории, каждая новая функция идёт через задачу,
отдельную ветку и запрос на слияние.

---

## 1. Методология ветвления — GitFlow

| Ветка | Назначение | Откуда создаётся | Куда сливается |
|---|---|---|---|
| `main` | только выпущенные версии, каждая отмечена тегом `vX.Y.Z` | — | — |
| `develop` | интеграционная ветка, сюда сливаются готовые функции | `main` | `release/*` |
| `feature/<тема>` | новая функция / доработка | `develop` | `develop` |
| `release/<версия>` | подготовка выпуска (версия, документация) | `develop` | `main` + `develop` |
| `hotfix/<версия>` | срочное исправление выпущенной версии | `main` | `main` + `develop` |
| `conflict/<ветка>` | разрешение конфликта слияния ветки с `develop`/`main` | целевая ветка | целевая ветка |

Слияние — только `git merge --no-ff` (в истории видно, какие коммиты пришли из ветки)
и только после зелёного `make verify` и CI.

## 1.1 Конфликты слияния — только через ветку `conflict/<ветка>`

Конфликт **никогда не разрешается прямо в `develop` или `main`**: защищённая ветка
не должна оказаться в промежуточном состоянии с маркерами `<<<<<<<` или с
непроверенным результатом ручной правки.

```bash
# PR feature/X → develop показывает конфликт
git checkout develop && git pull
git checkout -b conflict/X              # ветка разрешения от актуальной целевой ветки
git merge --no-ff feature/X             # CONFLICT … — правим файлы вручную
git add <файлы> && git commit           # коммит слияния: что конфликтовало и как решено
make verify                             # результат разрешения проверяется полностью
git push -u origin conflict/X           # CI проверяет ветку разрешения (on: push conflict/**)
# PR conflict/X → develop: ревью именно разрешения конфликта, CI зелёный
git checkout develop && git merge --no-ff conflict/X   # чистое слияние без конфликтов
```

Так в `develop` попадает только уже проверенный результат, а в истории видно,
кто, где и как разрешил конфликт.

## 2. Жизненный цикл изменения

```
задача (Issue)
  → ветка feature/<тема> от develop
    → коммиты (осмысленные, атомарные)
      → make verify локально (и make container-check, если менялось контейнерное окружение)
        → Pull Request в develop → CI зелёный → ревью второго участника
          → merge --no-ff в develop
            → release/<версия> → merge в main → тег vX.Y.Z
```

## 3. Обязательные команды перед коммитом и слиянием

```bash
make verify            # весь обязательный набор локальных проверок
make container-check   # обязательно, если менялись Dockerfile / compose / nginx
```

Коммит, слияние ветки и сдача работы **запрещены**, если команды завершаются с ошибкой.
В CI выполняются **те же** цели Makefile (`scripts/ci.sh` вызывает `make`), поэтому
результат локальной и серверной проверки совпадает.

### Что запускает `make verify`

| Шаг | Команда | Что проверяет |
|-----|---------|---------------|
| 1 | `make policy` | правила ниже (пропуски тестов, пороги, исключения анализаторов) |
| 2 | `make lint` | `ruff check` + `ruff format --check` (стиль, импорты, bugbear, security-правила) |
| 3 | `make sast` | `bandit` — статический анализ безопасности, отчёт `reports/bandit.json` |
| 4 | `make migrate-check` | цепочка миграций на чистой БД + `alembic check` (модели = миграции) |
| 5 | `make test` | unit + интеграционные тесты, JUnit и покрытие в `reports/`, порог покрытия |
| 6 | `make mutation` | мутационное тестирование бизнес-правил, порог mutation score |

## 4. Запрещено без обоснования

Нарушения обнаруживает `scripts/check_policy.py` (шаг `make policy`):

1. **Пропуск тестов** — `pytest.mark.skip`, `skipif`, `xfail`, `pytest.skip()`.
   Допустимо только если в `reason` есть слово «обоснование».
2. **Снижение порогов** — `fail_under` в `pyproject.toml` не ниже 85,
   `MUTATION_MIN` в `Makefile` не ниже 90. Удаление `--strict-markers` запрещено.
3. **Исключения анализаторов**:
   - `# noqa` / `# nosec` — только с кодом правила **и** пояснением;
   - новые `ignore` / `per-file-ignores` в ruff и `skips` в bandit — только через
     изменение списка разрешённых исключений в `scripts/check_policy.py`.
4. **Удаление шага из `make verify`**.
5. **Контейнерное окружение** (проверяет `make container-lint`, входит в `make container-check`):
   тег `latest`, запуск от root, секреты в образе, отключённый healthcheck,
   публикация лишних портов.
6. Коммитить `.env`, ключи, пароли, токены; `git push --force` в `main`/`develop`;
   сливать ветку с красным CI.

## 5. Критические файлы приёмки

`Makefile`, `pyproject.toml`, `scripts/check_policy.py`, `scripts/container_check.sh`,
`scripts/ci.sh`, `tests/**`, `alembic/versions/**`, `Dockerfile`, `docker-compose.yml`,
`.github/**`, `.gitleaks.toml`, `requirements*.txt`.

Их изменение видно в запросе на слияние и требует отдельного одобрения
владельца кода (`.github/CODEOWNERS` + правило защиты ветки «Require review from Code Owners»).

## 6. Миграции

- Любое изменение моделей сопровождается новой миграцией (`make migrate-new MSG="..."`).
- Применённые миграции не редактируются — только новая ревизия.
- Миграция должна работать на БД с данными и иметь рабочий `downgrade`.

## 7. Коммиты

Формат: `<тип>(<область>): <что сделано>` или `ЛРN — <что сделано>`;
типы `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`.

## 8. Версионирование

[Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`. Тег ставится на
коммит слияния `release/*` в `main`:

```bash
git tag -a v0.4.0 -m "ЛР4: контейнеризация"
git push origin v0.4.0
```

## 9. Конфигурация и секреты

- Все настройки — только через переменные окружения; шаблон — `.env.example`.
- Реальные значения — в `.env` (в `.gitignore`), на серверах — в `/etc/cityduma/*.env`,
  в CI — в защищённых переменных (Secrets) репозитория.
- Поиск секретов: `gitleaks` в CI.

## 10. Порядок приёмки

1. Задача → ветка → коммиты → PR → зелёный CI → ревью → merge → тег.
2. `make verify` проходит локально.
3. `.env`, ключи и локальные файлы не попадают в репозиторий (`git status`, `git check-ignore -v .env`).
4. Живая демонстрация и контрольное изменение / отказ.
